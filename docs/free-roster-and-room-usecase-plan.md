# План: свободный состав во время игры и база `RoomUseCase`

Документ фиксирует решения, принятые при обсуждении (grill-me), и порядок их реализации.
Работа ведётся по TDD: сначала тесты, затем код.

Связанные документы: [shop-and-engine-spec.md](./shop-and-engine-spec.md).

---

## 1. Цели

1. Игроки могут входить в комнату и выходить из неё во время игры.
2. Составом команд во время игры управляет лидер лобби. Команды можно удалять по ходу, если они стали не нужны.
3. Ротация команд и объясняющих не ломается при изменении состава.
4. Повторяющийся каркас use-case'ов (lock → load → dispatch → save → notify) выносится в базовый класс.

Не входит в план: горизонтальное масштабирование (`RoomFifoQueueService` остаётся in-process), CQRS/CommandBus.

---

## 2. Принятые решения

| # | Тема | Решение |
|---|------|---------|
| 1 | Вход во время игры | Вошедший попадает в зрители (`spectators`). В команду его ставит только лидер лобби |
| 2 | Отключение и выход | Отключение (`SET_PLAYER_OFFLINE`) держит место: игрок `isOnline = false`, остаётся в команде и возвращается на то же место. Явный «выйти» (`LEAVE_GAME`) удаляет игрока из команды |
| 3 | Пустая команда | Остаётся в игре. Следующий раунд нельзя начать, пока в каждой команде нет хотя бы одного онлайн-игрока. Лидер может удалить команду вручную. Если опустела играющая сейчас команда, раунд завершается |
| 4 | Таймер раунда | Если объясняющий офлайн или удалён, таймер ставится на паузу и продолжается с остатка после возврата или замены через `setExplainer`. Лидер может завершить раунд вручную в любой момент |
| 5 | Очередь объясняющих | Курсор хранится по `id` (`lastExplainerId`), а не по индексу. Следующий объясняющий — следующий онлайн-игрок по кругу в порядке `playerIds`. Если курсорный игрок ушёл, берётся тот, кто стоял бы после него |
| 6 | Данные ушедшего | Счёт команды не меняется. Снимок игрока (`id`, имя, команда, личный счёт) сохраняется в `state.leftPlayers` для истории и итогов. Слова шляпы остаются в пуле |
| 7 | Передача владения | При явном выходе лидера владение сразу переходит первому онлайн-игроку (порядок входа в комнату, игроки команд выше зрителей). При отключении лидера — через таймаут (по умолчанию 60 с), если он не вернулся |
| 8 | Минимум команд | Нельзя удалить команду, если останется меньше 2. Нельзя удалить команду, которая играет прямо сейчас. Для остановки игры есть `endGame` |
| 9 | Режим шляпы | Ввод слов после старта закрыт. Поздние игроки играют без обязанности добавлять слова |

### Предположения (приняты без отдельного вопроса)

- Переходы между командами и создание команд во время игры доступны только лидеру.
- Кик во время игры работает как явный выход: снимок игрока сохраняется, владение не меняется.
- В статусе `LOBBY` поведение остаётся прежним: игроки сами выбирают команду, выход удаляет игрока без снимка.

## 3. Текущее состояние кода (по результатам аудита)

- `JOIN_GAME` не проверяет статус игры, игрок попадает в `spectators`.
- `LEAVE_GAME` не проверяет статус и не учитывает игровое состояние: `currentRound.explainerId` остаётся «висеть», владение не передаётся.
- `MOVE_TO_TEAM`, `MOVE_TO_SPECTATORS`, `DELETE_TEAM` требуют `LOBBY`.
- `lastExplainerIndex` — индекс в `team.playerIds`. После удаления игрока индекс указывает на другого.
- `NEXT_ROUND` выбирает следующую команду по индексу и может выбрать пустую, а объясняющим поставить `""`. Офлайн-игроки могут стать объясняющими.
- `ownerId` нигде не меняется после создания комнаты.
- Остаток легаси: каталог `backend/src/modules/game/domain/addons/` (`addon.types.ts`, `base/*`) — дубль старой системы, нигде не используется.
- Каркас «lock → load → dispatch → save → emit» повторяется в 27 use-case'ах; не используют его только `create-game` (комнаты ещё нет) и сам репозиторий.

## 4. Изменения доменной модели

### 4.1. Состояние (`state/game.state.ts`)

| Поле | Где | Назначение |
|------|-----|-----------|
| `lastExplainerId?: string` | `TeamState` | Курсор очереди объясняющих вместо `lastExplainerIndex` |
| `leftPlayers: LeftPlayerState[]` | `GameState` | Снимки ушедших игроков |
| `pausedAt?: number`, `remainingMs?: number` | `RoundState` | Пауза таймера, остаток времени |
| `ownerOfflineSince?: number \| null` | `GameState` | Метка начала отключения лидера |

```ts
interface LeftPlayerState {
  id: string;
  name: string;
  teamId: string | null;
  score: number;
  leftAt: number;
}
```

`lastExplainerIndex` удаляется после миграции (в проекте старых данных в Redis нет, живых игр хранить не нужно — подтвердить перед удалением).

### 4.2. Новые ошибки (`errors/`)

Все ошибки стандартизированы, наследуются от `GameError` и имеют код.

| Ошибка | Когда |
|--------|-------|
| `TeamHasNoOnlinePlayersError` | Старт/следующий раунд при команде без онлайн-игроков |
| `NotEnoughTeamsError` | Удаление команды оставит меньше 2 |
| `TeamIsPlayingError` | Удаление команды, которая играет сейчас |
| `NotRoomOwnerOnlyDuringGameError` (имя уточнить) | Игрок (не лидер) пытается менять состав в статусе, отличном от `LOBBY` |

### 4.3. Поведение действий

| Действие | В `LOBBY` | Во время игры |
|----------|-----------|---------------|
| `JOIN_GAME` | Как сейчас | Игрок → зрители; уже существующий игрок получает `isOnline = true` (если он объясняющий с паузой — таймер продолжается) |
| `LEAVE_GAME` | Как сейчас | Снимок в `leftPlayers`; удаление из `players`/команды/зрителей; передача владения, если ушёл лидер; если ушёл объясняющий — пауза таймера; если опустела играющая команда — завершение раунда; пересчёт курсора `lastExplainerId` на предшественника |
| `SET_PLAYER_OFFLINE` | Как сейчас | `isOnline = false`; для объясняющего — пауза; для лидера — `ownerOfflineSince` |
| `MOVE_TO_TEAM`, `MOVE_TO_SPECTATORS` | Как сейчас | Только лидер |
| `CREATE_TEAM` | Как сейчас | Только лидер |
| `DELETE_TEAM` | Как сейчас | Только лидер; проверки: `NotEnoughTeamsError`, `TeamIsPlayingError`; игроки команды уходят в зрители |
| `KICK_PLAYER` | Как сейчас | Как `LEAVE_GAME` + бан при `isPermanent`; владение не меняется |
| `SET_EXPLAINER` | Как сейчас | Замена объясняющего; если была пауза — таймер продолжается |
| `NEXT_ROUND` / `START_ROUND` | Как сейчас | Проверка «в каждой команде есть онлайн-игрок»; выбор следующей команды по `id`, не по индексу |
| `SUBMIT_CUSTOM_WORDS` | Как сейчас | Запрещено (как сейчас) |

### 4.4. Выбор следующего объясняющего

1. Берётся команда следующего раунда (по `activeTeamId`, затем следующая в массиве `teams`).
2. В `team.playerIds` находится позиция `lastExplainerId`.
3. Выбирается следующий онлайн-игрок по кругу.
4. Если курсорного игрока нет в списке (ушёл), курсор при выходе сдвигается на предшественника, поэтому «следующий» остаётся корректным.
5. Если онлайн-кандидатов нет — ошибка `TeamHasNoOnlinePlayersError`.

### 4.5. Передача владения

1. Кандидаты: онлайн-игроки в порядке входа; игроки команд выше зрителей.
2. При явном выходе лидера — сразу.
3. При отключении лидера — планировщик по таймауту (см. §5) отправляет действие `TRANSFER_OWNERSHIP` (новое), если лидер всё ещё офлайн.
4. Если кандидатов нет, владение остаётся за прежним лидером.

## 5. Application и инфраструктура

### 5.1. База `RoomUseCase`

Выносит из use-case'ов весь повторяющийся каркас:

```ts
export abstract class RoomUseCase<TDto extends { roomId: string }, TResult = RoomPrimitives> {
  protected notify: readonly RoomNotification[] = ["game"];

  async execute(dto: TDto, actor: UserDto): Promise<TResult> {
    return this.fifoQueue.run(dto.roomId, async () => {
      const engine = await this.gameSharedService.loadGame(dto.roomId);
      await this.beforeHandle?.(engine, dto, actor);
      const result = await this.handle(engine, dto, actor);
      await this.gameRepository.saveGame(engine);
      this.publish(engine);            // TEAMS_UPDATED, PLAYERS_UPDATED, GAME_UPDATED, ...
      return (result ?? engine.toPrimitives()) as TResult;
    });
  }

  protected abstract handle(engine: GameEngine, dto: TDto, actor: UserDto): TResult | Promise<TResult>;
  protected beforeHandle?(engine: GameEngine, dto: TDto, actor: UserDto): void | Promise<void>;
}
```

Что выносится в базу: lock, `loadGame`, `saveGame`, `toPrimitives()`, сборка payload'ов и эмиссия событий по декларативному `notify`, возвращаемое значение по умолчанию, логирование и метрики времени выполнения.

Вне базы остаются: `create-game` (нет комнаты), `join-game` (две комнаты, проверка кода) — или используют хуки.
Правило: вложенный `fifoQueue.run` одной комнаты в другой запрещён (риск deadlock).

Контракт ответов не меняется: `return` из use-case — ответ инициатору (ack), доменные события — рассылка остальным.

### 5.2. Планировщики

- [`RoundSchedulerService`](../backend/src/modules/game/application/round-scheduler.service.ts): поддержка паузы и возобновления (учёт `remainingMs`), перепланирование окончания раунда при продолжении.
- Новый `OwnerTransferScheduler` (или расширение существующего): таймер на отключение лидера (по умолчанию 60 с, настраивается), отмена при возврате лидера.
- Планировщики вызывают use-case'ы (не движок напрямую), чтобы пройти через lock комнаты.

### 5.3. Presentation

- `GameGateway`: после `JOIN_GAME` вошедший получает публичное состояние как зритель; приватное слово по-прежнему получает только объясняющий.
- События о паузе и возобновлении таймера рассылаются через `ROUND_UPDATED`.
- Новых socket-событий не требуется, кроме возможного `owner:transferred` (опционально, достаточно `GAME_UPDATED`).

### 5.4. History

- `history` использует `leftPlayers` при сохранении итогов: ушедшие игроки остаются в `participants` с последним личным счётом.
- Раунды, сыгранные до ухода игрока, остаются в истории без изменений.

## 7. Сценарии для ручной проверки

1. Игрок заходит в идущую игру → виден как зритель, лидер переводит его в команду.
2. Объясняющий закрывает вкладку → таймер на паузе, после возврата продолжается.
3. Объясняющий нажимает «выйти» → таймер на паузе, лидер назначает нового через `setExplainer`, таймер продолжается.
4. Последний игрок играющей команды выходит → раунд завершается; следующий раунд недоступен, пока в команде нет онлайн-игрока.
5. Лидер удаляет пустую команду → игра продолжается с оставшимися (при ≥ 2 командах).
6. Лидер пытается удалить предпоследнюю или играющую команду → получает ошибку.
7. Лидер выходит → владение сразу у следующего; лидер закрывает вкладку → владение через 60 с.
8. Игрок выходит и итоги игры сохраняются в `history` с его последним счётом.
9. В режиме шляпы игрок входит после старта → играет без добавления слов.
